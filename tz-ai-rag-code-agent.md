# Техническое задание: AI-агент для поиска релевантных мест в кодовой базе с использованием RAG

## 1. Назначение документа

Документ фиксирует актуальные требования и согласованный контракт приложения; конфигурация LLM и административный доступ определяются разделами ниже.

Цель приложения: дать пользователю локальный веб-интерфейс, в котором он выбирает папку проекта на своем компьютере, приложение индексирует кодовую базу через RAG, а затем по текстовым запросам пользователя находит и показывает наиболее релевантные участки кода.

## 2. Краткое описание продукта

Необходимо разработать локальное веб-приложение с двумя основными частями:

1. Frontend: React/Vite приложение в стиле Windows 11.
2. Backend: локальный Node.js/NestJS сервер, который имеет доступ к файловой системе пользователя, сканирует выбранную папку проекта, строит локальный RAG-индекс и обрабатывает запросы поиска.

Пользовательский сценарий:

1. Пользователь запускает локальный backend и frontend.
2. В левой колонке интерфейса нажимает кнопку выбора папки проекта.
3. Backend открывает системный диалог выбора директории или принимает путь, выбранный через поддерживаемый механизм.
4. Backend сканирует проект, исключает нерелевантные и опасные файлы, разбивает код на чанки, получает embeddings через OpenAI-compatible и сохраняет индекс локально в LanceDB/SQLite.
5. Пользователь вводит вопрос в чат.
6. Frontend отправляет сообщение на backend.
7. Backend выполняет retrieval по индексу, формирует контекст, отправляет запрос через OpenAI-compatible к модели openai/gpt-4.1.
8. Модель возвращает объяснение и список найденных мест в коде.
9. Справа отображается найденный код с путями файлов, номерами строк, подсветкой синтаксиса и краткими пояснениями.

## 3. Выбранная архитектура

### 3.1. Компоненты

1. Frontend:
   - React.
   - Vite.
   - TypeScript.
   - CSS Modules, SCSS или vanilla CSS с дизайн-токенами Windows 11.
   - Monaco Editor или CodeMirror для отображения кода справа.
   - Клиентский state management: Zustand или React Context.

2. Backend:
   - Node.js.
   - NestJS.
   - TypeScript.
   - REST API для базового управления проектами, индексом и чатом.
   - WebSocket или Server-Sent Events для прогресса индексации и потоковой генерации ответа.

3. RAG-хранилище:
   - LanceDB для векторного поиска.
   - SQLite для метаданных проекта, файлов, чанков, истории чата, настроек и состояния индексации.

4. LLM и embeddings:
   - Backend использует `LlmService` вместо прежнего `OpenRouterService`; API интеграция совместима с OpenAI API.
   - Base URL по умолчанию `https://polza.ai/api/v1`.
   - Chat-модель по умолчанию: `openai/gpt-4.1`.
   - Embedding-модель по умолчанию: `perplexity/pplx-embed-v1-4b`.
   - Конфигурационные файлы: `apps/backend/.env` и образец `apps/backend/.env.example`. Переменные `LLM_BASE_URL`, `LLM_CHAT_MODEL`, `LLM_EMBEDDING_MODEL` и `LLM_API_KEY` задаются в `apps/backend/.env`. Backend загружает и сохраняет этот файл независимо от cwd; корневой `.env` не используется.

### 3.2. Обоснование выбора

1. React/Vite обеспечивает быстрый frontend, удобную разработку и простую сборку.
2. NestJS подходит для структурированного backend с модулями, сервисами, dependency injection и типизацией.
3. LanceDB хорошо подходит для локального векторного поиска и хранения embeddings.
4. SQLite удобен как локальная база метаданных без отдельного сервера.
5. OpenAI-compatible API предоставляет единый конфигурируемый интерфейс для chat completion и embeddings; реализация использует `LLM_API_KEY`, `LLM_BASE_URL`, `LLM_CHAT_MODEL` и `LLM_EMBEDDING_MODEL`.
6. Разделение frontend/backend необходимо, потому что браузер не должен напрямую иметь полный доступ к локальной файловой системе.

## 4. Основные функциональные требования

### 4.1. Выбор папки проекта

1. В левой колонке сверху должна быть кнопка Выбрать папку проекта.
2. После выбора папки frontend должен показать:
   - название проекта;
   - абсолютный или сокращенный путь;
   - статус индексации;
   - количество найденных файлов;
   - количество проиндексированных чанков.
3. Backend должен проверять, что выбранный путь существует и является директорией.
4. Backend должен запрещать индексировать системные и опасные директории по умолчанию, если они не разрешены явно.
5. Повторный выбор другой папки должен сбрасывать активный индекс или создавать новый project profile.

### 4.2. Администраторская настройка API и credentials

1. API key может ввести только администратор в отдельной панели «Настройка API» из header и только после успешного входа. На главном экране обычного пользователя нет блока настройки: показываются только статус наличия ключа и указание обратиться к администратору.
2. В панели администратора поле API key должно вести себя как пароль:
   - вводимые символы скрыты;
   - значение не отображается в открытом виде;
   - рядом допускается кнопка временного показа, но по умолчанию ключ всегда скрыт;
   - ключ не должен попадать в историю чата, логи frontend, URL, query string или сообщения об ошибках.
3. Ключ сохраняется backend в `apps/backend/.env` и в runtime-памяти:
   - сначала backend атомарно сохраняет значение в конфигурационный файл (на обычной файловой системе — временный файл и rename), затем обновляет память; если запись не удалась, активное значение не меняется;
   - для single-file Docker bind mount допускается fallback записи на месте с backup/restore при ошибке; абсолютная атомарность в этом сценарии не гарантируется.
4. `apps/backend/.env` загружается и сохраняется независимо от cwd; пример конфигурации — `apps/backend/.env.example`. В `.env` поддерживаются `ADMIN_LOGIN=admin`, `ADMIN_PASSWORD=`, `LLM_API_KEY=`, `LLM_BASE_URL=https://polza.ai/api/v1`, `LLM_CHAT_MODEL=openai/gpt-4.1`, `LLM_EMBEDDING_MODEL=perplexity/pplx-embed-v1-4b`. При локальной настройке корневой `password.txt` остаётся gitignored источником пароля администратора; его значение задаётся как `ADMIN_PASSWORD`. Пустые логин или пароль запрещают вход. Создание конфигурации не перезаписывает существующий файл или значения; `OPENROUTER_*` автоматически не мигрируются. Если LLM API key не задан, status показывает `hasApiKey: false`, а LLM-зависимые действия показывают понятное состояние.

### 4.2.1. Раздел администратора «Индексы»

1. В отдельном разделе «Индексы» после входа администратора отображаются параметры индексации и доступны действия проверки/сброса.
2. Статус загружается через `GET /api/settings/indexes/status` с `Authorization: Bearer <token>` и возвращает `{embeddingModel, storedEmbeddingModel, requiresReset, indexedProjects, indexedChunks}`. `requiresReset` указывает на изменение fingerprint `{baseUrl, embeddingModel}` или legacy-индекс без сохранённых metadata.
3. Fingerprint `{baseUrl, embeddingModel}` хранится постоянно в SQLite. Смена base URL или embedding-модели требует явного сброса, в том числе если новая модель имеет ту же размерность. Для индексов без fingerprint/metadata также требуется явный сброс; автоматически удалять или переиспользовать такие индексы запрещено.
4. Сброс выполняется только явным действием через двухшаговый UI: сначала показать подтверждение/отмену и пояснить, что после сброса потребуется переиндексация; до подтверждения ничего не удалять.
5. Подтверждение отправляет `POST /api/settings/indexes/reset` с Bearer token и телом `{confirm:true}`; успешный ответ — `{success:true}`. При активной индексации сброс отклоняется с HTTP 409.
6. Сброс глобальный: он очищает общую LanceDB chunks table/schema и cache, а также SQLite `files` и `chunks` для всех проектов. Сущности `projects`, `conversations`, `messages` и история чатов сохраняются. Всем проектам задаются `status=idle` и `lastIndexedAt=null`.
7. После успешного сброса пользователь должен заново проиндексировать нужные проекты. Индексы автоматически не удаляются.

### 4.4. Индексация и RAG

Backend должен реализовать pipeline:

1. Project scan:
   - получить список файлов;
   - применить ignore rules;
   - вычислить hash содержимого каждого файла;
   - определить измененные, новые и удаленные файлы.

2. Parsing and chunking:
   - читать файл как текст;
   - определить язык по расширению;
   - разбить файл на чанки с учетом структуры кода;
   - сохранять для каждого чанка путь файла, диапазон строк, язык, имя ближайшей функции или класса при возможности;
   - использовать overlap между чанками для сохранения контекста.

3. Embeddings:
   - отправлять чанки в embedding API через OpenAI-compatible;
   - батчировать запросы;
   - учитывать rate limits;
   - повторять временно неуспешные запросы с backoff;
   - сохранять embedding и metadata локально.

4. Vector search:
   - по пользовательскому вопросу получить embedding запроса;
   - найти top-K релевантных чанков в LanceDB;
   - дополнительно применить keyword search по SQLite FTS или аналогичному механизму;
   - объединить результаты vector search и keyword search;
   - применить reranking эвристиками: совпадение имени файла, пути, символов, языка, импортов, экспортов, тестов.

5. Context assembly:
   - собрать ограниченный контекст для LLM;
   - включить только релевантные чанки;
   - добавить метаданные: путь файла, строки, язык, краткое описание;
   - не отправлять файлы целиком без необходимости;
   - при нехватке контекста вернуть пользователю уточняющий вопрос или список возможных мест.

6. Answer generation:
   - отправить в OpenAI-compatible запрос к openai/gpt-4.1;
   - модель должна вернуть структурированный ответ: краткое объяснение, список найденных файлов и диапазонов строк, уверенность, кодовые фрагменты.

## 6. Backend API

### 6.1. Общие требования

1. Все API доступны только на localhost по умолчанию.
2. CORS разрешен только для frontend origin.
3. Ответы должны быть типизированы.
4. Ошибки должны возвращаться в едином формате:
   - code;
   - message;
   - details;
   - requestId.

### 6.2. REST endpoints и контракт настроек

Настройки API используют следующие точные контракты:

- `GET /api/settings/status` → `{ "hasApiKey": boolean }`. Endpoint не возвращает ключ или другие секреты.
- `POST /api/settings/admin/login` принимает `{ "login": string, "password": string }` и возвращает `{ "token": string, "expiresAt": number }`, где `expiresAt` — Unix epoch в миллисекундах. При пустых `ADMIN_LOGIN` или `ADMIN_PASSWORD` вход запрещён.
- `POST /api/settings/admin/logout` требует `Authorization: Bearer <token>` и возвращает `{ "success": true }`.
- `POST /api/settings/api-key` требует `Authorization: Bearer <token>`, принимает `{ "apiKey": string }` и возвращает `{ "success": true }`. Секрет не включается в ответ.
- `GET /api/settings/indexes/status` требует `Authorization: Bearer <token>` и возвращает `{ "embeddingModel": string, "storedEmbeddingModel": string | null, "requiresReset": boolean, "indexedProjects": number, "indexedChunks": number }`.
- `POST /api/settings/indexes/reset` требует `Authorization: Bearer <token>`, принимает `{ "confirm": true }` и при успехе возвращает `{ "success": true }`. Если любая индексация активна, запрос отклоняется с HTTP 409; при любом другом теле, кроме явного подтверждения `true`, сброс не выполняется.

Admin token — криптографически случайный bearer token, хранится только в памяти frontend React и backend, действует 1 час, не сохраняется в browser storage и становится недействительным при logout, истечении срока или перезапуске backend. Вход защищён ограничением частоты неудачных попыток (brute-force limit). API key записывается в `apps/backend/.env` раньше обновления runtime-памяти; ошибки записи не должны изменять активное значение или раскрывать секрет. `GET /api/settings/indexes/status` и `POST /api/settings/indexes/reset` требуют той же авторизации администратора.

Остальные REST endpoints приложения:

1. POST /api/projects/select
   - запускает выбор или регистрацию папки проекта;
   - принимает путь, если системный диалог недоступен;
   - возвращает projectId, name, path, status.

2. POST /api/projects/index
   - запускает индексацию projectId.

3. GET /api/projects/:projectId/status
   - возвращает состояние сканирования и индексации.

4. POST /api/chat/message
   - принимает projectId, message, conversationId;
   - выполняет retrieval и LLM generation;
   - возвращает ответ и найденные code references.

5. GET /api/files/snippet
   - принимает projectId, filePath, startLine, endLine;
   - возвращает текст фрагмента с контекстными строками.

6. GET /api/search
   - выполняет только retrieval без генерации ответа;
   - полезно для отладки и быстрых поисковых запросов.

### 6.3. Streaming

Для событий использовать WebSocket или Server-Sent Events.

События:

## 8. OpenAI-compatible интеграция

### 8.1. Требования

1. Все запросы к OpenAI-compatible идут только с backend.
2. Frontend не должен напрямую обращаться к OpenAI-compatible.
3. Ни API key, ни admin bearer token не сохраняются в browser storage; frontend хранит токен только в runtime-памяти React.
4. Для chat completion использовать модель openai/gpt-4.1.
5. Для embeddings использовать `LLM_EMBEDDING_MODEL`, по умолчанию `perplexity/pplx-embed-v1-4b`; base URL по умолчанию `https://polza.ai/api/v1`, chat model — `openai/gpt-4.1`.
6. Добавить таймауты, retry, rate limit handling и понятные ошибки.

### 8.2. System prompt для chat-модели

Модель должна отвечать как агент поиска по коду.

Требования к ответу:

1. Не выдумывать файлы и строки.
2. Использовать только найденный RAG-контекст.
3. Если уверенность низкая, явно сообщить об этом.
4. Возвращать ссылки на конкретные файлы и строки.
5. Давать краткое объяснение, почему найденный фрагмент релевантен.
6. Не предлагать правки кода, если пользователь просит только найти место.
7. Если пользователь просит объяснить место, дать объяснение на основе кода.

## 9. Безопасность и приватность

1. Кодовая база пользователя остается на локальном компьютере.
2. Во внешние сервисы отправляются только выбранные чанки или embeddings-запросы, необходимые для RAG, если embeddings выполняются через OpenAI-compatible.
3. Пользователь должен быть предупрежден, что при использовании OpenAI-compatible часть кода может отправляться во внешний сервис для embeddings и генерации ответа.
4. Добавить настройку exclude secrets.
5. Никогда не индексировать реальные .env файлы по умолчанию.
6. Никогда не логировать API key, admin password или bearer token; секреты не включать в API-ответы и сообщения об ошибках.
7. Маскировать ключ в администраторской панели.
8. Backend слушает только 127.0.0.1 по умолчанию.
9. Запретить произвольное чтение файлов вне выбранного project root.
10. Нормализовать и проверять пути, чтобы избежать path traversal.
11. Добавить лимиты размера файла, количества файлов, общего размера проекта и размера запроса.
12. Добавить администраторский раздел «Индексы» с контрактами статуса и явного общего сброса из разделов 4.2.1 и 6.2. Сохранять в SQLite fingerprint `{baseUrl, embeddingModel}`; смена любого значения, включая embedding-модель той же размерности, и legacy-индексы без metadata требуют явного сброса, без автоматического удаления. Сброс очищает общую LanceDB chunks table/schema и cache, а также SQLite `files` и `chunks` всех проектов; проекты, conversations, messages и история сохраняются, статус проектов становится `idle`, `lastIndexedAt` — `null`. UI требует подтверждения/отмены и объясняет необходимость переиндексации; во время активной индексации API отвечает 409. `npm run clean:data` может удалить локальные данные и историю: использовать только после проверки содержимого и при осознанной необходимости.

При production-развёртывании HTTPS обязателен для входа и передачи API key. Целевой `apps/backend/.env` должен быть исключён из Git и доступен только backend-процессу. Целевой Docker bind mount: `./apps/backend/.env:/app/apps/backend/.env` с доступом на чтение и запись; для single-file bind mount запись на месте с backup/restore является fallback и не гарантирует абсолютную атомарность. Физический перенос конфигурационных файлов пока заблокирован; Docker-файлы этой спецификацией не меняются.

Администраторская авторизация защищает только настройки, API key и административный раздел «Индексы»; основной чат и остальные операции не получают multiuser ACL и остаются доверенным локальным RAG.

## 10. Нефункциональные требования

### 10.1. Производительность

1. Индексация должна быть инкрементальной.
2. Неизмененные файлы не должны переиндексироваться.
3. Большие файлы должны обрабатываться потоково или пропускаться по лимиту.
4. UI не должен блокироваться во время индексации.
5. Пользователь должен видеть прогресс.

3. При перезапуске backend приложение должно восстанавливать список ранее выбранных проектов и состояние индекса, если данные сохранены.

### 10.3. Доступность

1. Все интерактивные элементы доступны с клавиатуры.
2. Поля имеют label.
3. Контрастность соответствует базовым требованиям WCAG.
4. Для прогресса индексации должны быть текстовые статусы, не только цвет.

## 13. Критерии приемки

Приложение считается готовым, если выполняются условия:

1. Пользователь может открыть UI в браузере.
2. Левая колонка занимает 40 процентов, правая — 60 процентов.
3. UI визуально соответствует Windows 11 стилю.
4. В левой колонке сверху есть кнопка выбора папки проекта.
5. API key может вводить только администратор в отдельной панели «Настройка API» в header после входа; на главном экране обычного пользователя есть только статус и обращение к администратору.
6. Реализованы точные контракты `GET /api/settings/status` → `{hasApiKey}`, login → `{token, expiresAt}` (epoch ms), logout и API-key save → `{success:true}`; ни один ответ не раскрывает секрет.
7. После выбора проекта backend сканирует файлы и строит локальный индекс.
8. Пользователь видит прогресс индексации.
9. После индексации пользователь может задать вопрос в чат.
10. Запрос отправляется через backend в OpenAI-compatible с использованием openai/gpt-4.1.
11. RAG retrieval возвращает релевантные чанки из проекта.
12. Правая колонка отображает найденный код с путями файлов и номерами строк.
13. Клик по результату в чате открывает соответствующий код справа.
14. Секретные файлы не индексируются по умолчанию.
15. При отсутствии API key или проекта UI показывает понятное состояние.
16. При ошибке OpenAI-compatible приложение показывает понятную ошибку без раскрытия секретов.
17. Администраторский раздел «Индексы» предоставляет авторизованные `GET /api/settings/indexes/status` → `{embeddingModel,storedEmbeddingModel,requiresReset,indexedProjects,indexedChunks}` и `POST /api/settings/indexes/reset` с `{confirm:true}` → `{success:true}`; сброс глобален, возвращает 409 при активной индексации, очищает векторный индекс/LanceDB cache и SQLite files/chunks, сохраняет projects и историю conversations/messages, а всем проектам выставляет idle и `lastIndexedAt=null`.
18. Повторная индексация измененного проекта обновляет только измененные файлы.
19. Admin token является случайным Bearer token с TTL 1 час, хранится только в runtime-памяти frontend/backend, не сохраняется в browser storage и аннулируется logout/restart; вход имеет brute-force limits.
20. На production вход и передача API key защищены HTTPS; целевой `apps/backend/.env` не включается в Git или Docker image и доступен backend-процессу. Основной чат не получает multiuser ACL.
21. На форме admin login поле пароля на 20% ниже стандартного input; высота других полей не меняется.

## 14. Тестовые сценарии

### 14.1. Выбор проекта

1. Запустить frontend и backend.
2. Нажать Выбрать папку проекта.
3. Выбрать тестовый проект.
4. Проверить, что UI показывает имя проекта и путь.
5. Проверить, что backend создал projectId.

### 14.2. Администраторская авторизация и API key

1. При пустом `ADMIN_LOGIN` или `ADMIN_PASSWORD` проверить, что login запрещён.
2. С безопасно заданными credentials вызвать `POST /api/settings/admin/login` с `{login,password}` и проверить `{token,expiresAt}` с временем истечения через 1 час.
3. Убедиться, что неверные попытки ограничиваются, а bearer token не сохраняется в browser storage.
4. Проверить `GET /api/settings/status`: он возвращает только `{hasApiKey}`.
5. Авторизованным Bearer вызвать `POST /api/settings/api-key` с `{apiKey}`; проверить `{success:true}`, сохранение в целевой `apps/backend/.env` до смены runtime-памяти и отсутствие секрета в ответах/логах.
6. Проверить, что logout через `POST /api/settings/admin/logout` отзывает token; после logout и backend restart token недействителен.
7. Проверить TTL token по `expiresAt`.
8. Убедиться, что обычный пользователь не видит настройки API и раздел «Индексы», а видит только статус и обращение к администратору.
9. Проверить форму входа: поле пароля на 20% ниже по высоте, прочие input не меняют высоту.

### 14.3. Индексация

1. Запустить индексацию.
2. Проверить прогресс.
3. Проверить, что node_modules и .git пропущены.
4. Проверить, что .env не индексируется.
5. Проверить, что LanceDB и SQLite содержат записи чанков.
6. Проверить, что fingerprint `{baseUrl, embeddingModel}` сохраняется в SQLite; изменение base URL/модели, в том числе при той же размерности, и legacy-индекс без metadata требуют явного сброса и никогда не удаляются автоматически.
7. С Bearer проверить `GET /api/settings/indexes/status` и точный ответ `{embeddingModel,storedEmbeddingModel,requiresReset,indexedProjects,indexedChunks}`.
8. Проверить двухшаговый UI сброса: отмена не изменяет данные, подтверждение отправляет `{confirm:true}` и объясняет необходимость переиндексации.
9. При активной индексации reset возвращает HTTP 409; в idle-состоянии успешный глобальный reset удаляет LanceDB chunks table/schema/cache и SQLite files/chunks всех проектов, но сохраняет projects и conversations/messages/history, выставляет проектам idle и `lastIndexedAt=null`, и возвращает `{success:true}`.
10. Убедиться, что после успешного сброса для поиска требуется переиндексация.

### 14.4. Поиск места в коде

1. Задать вопрос: Где реализован роут логина?
2. Проверить, что система возвращает файлы и строки.
3. Проверить, что справа открывается код.
4. Проверить, что найденные строки подсвечены.

### 14.5. Ошибки

1. Запустить систему с пустым `LLM_API_KEY`.
2. Проверить статус отсутствия ключа и понятное сообщение при попытке LLM-зависимого действия без настройки.
3. Остановить интернет и повторить запрос.
4. Проверить retry или понятное сообщение о сетевой ошибке.

## 15. Ограничения и допущения

1. Приложение работает локально.
2. Backend имеет доступ к файловой системе только в рамках выбранного project root.
3. Выбор папки в обычном браузере напрямую невозможен для backend без посредника, поэтому требуется один из механизмов:
   - frontend получает путь через поддерживаемый локальный picker;
   - backend открывает системный диалог через Node.js библиотеку;
   - пользователь вручную вводит путь как fallback.
4. Основной целевой сценарий: запуск на машине разработчика.
5. Внешний OpenAI-compatible API используется для chat generation и embeddings, поэтому пользователь должен понимать, что релевантные фрагменты кода могут отправляться во внешний API.
6. Администраторская авторизация защищает настройки API, но не добавляет многопользовательскую авторизацию к остальным операциям приложения.
