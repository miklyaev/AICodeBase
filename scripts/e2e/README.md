# E2E: настройки API, RAG fixture и обслуживание индексов

Оба runner проверяют настоящее приложение через Playwright, без mock и OS picker. Работают из любой текущей папки: пути вычисляются относительно runner. `run.cjs` — платный RAG-сценарий без очистки индексов; `run-maintenance.cjs` — отдельный бесплатный сценарий обслуживания, удаляющий только индексы изолированного тестового стенда.

## Предусловия

- Windows 10, Node.js и уже установленные `playwright` и `dotenv`. Runner ничего не устанавливает и не скачивает браузеры.
- Доступен установленный Edge или Chrome. Порядок запуска: `msedge` → `chrome` → уже установленный bundled Chromium.
- Backend доступен на `http://localhost:3181`, frontend — на `http://localhost:5173`. Frontend должен обращаться к этому backend.
- Backend запущен с отдельной тестовой БД, cwd `.e2e-runtime/backend`; реальные рабочие БД/индексы использовать нельзя. Только данные изолированы: настройки читаются и сохраняются в настоящей `apps/backend/.env`. Тест намеренно сохраняет предоставленный ключ через UI и оставляет его в конфигурации после завершения.
- В `apps/backend/.env` задан `ADMIN_LOGIN`; пароль backend настроен из корневого `password.txt`. Для runner логин задаётся через `$env:E2E_ADMIN_LOGIN` (по умолчанию `admin`) и должен совпадать с настройкой backend. Ключ находится в `D:/NeuroNet/Routers/Polza.ai/api_key.txt`.
- В текущем минутном окне ещё не было попыток входа с IP runner. После неудачного повторного запуска дождитесь окончания окна или перезапустите только isolated backend; runner не повторяет входы автоматически.

Секретные файлы читает только запущенный Node.js процесс в память; значения никогда не выводятся. Не передавайте секреты аргументами командной строки. Не включайте `DEBUG=pw:*`, внешнюю запись трафика, trace/HAR или скриншоты.

## Команды PowerShell

Если зависимости ещё не установлены:

```powershell
npm install
npm install --no-save --package-lock=false playwright
```

В корне репозитория, если supervisor ещё не запущен:

```powershell
node scripts/e2e/serve.cjs
```

В другом терминале, **после готовности серверов**:

```powershell
node --check scripts/e2e/run.cjs
node scripts/e2e/run.cjs
```

Для уже запущенных серверов на других локальных портах:

```powershell
$env:E2E_FRONTEND_URL = 'http://localhost:5173'
$env:E2E_BACKEND_URL = 'http://localhost:3181'
node scripts/e2e/run.cjs
```

Разрешены только HTTP loopback URL без credentials/query/hash. Не запускайте runner параллельно с другим прогоном.

После проверки остановите только тестовый стенд:

```powershell
node -e "const c=require('./.e2e-runtime/control.json'); fetch(c.url+'/stop',{method:'POST',headers:{'X-E2E-Control':c.token}}).then(r=>console.log('Stop status:',r.status))"
```

## Проверки и стоимость

1. Главная без старой формы ключа; при отсутствии ключа есть уведомление для пользователя.
2. Доступно именованный диалог, Escape/закрытие/повторное открытие, неверный пароль → правильный вход, маскирование пароля и ключа.
3. Сохранение настоящего ключа через UI, очистка поля, logout и отзыв сессии (401), setter без авторизации (401), старый `/api/settings/openrouter-key` (404), лимит пяти входов/минуту (шестой запрос — 429).
4. Если существует `.e2e-runtime/control.json`, runner runtime читает `{url, token}` и вызывает `POST /restart-backend` с `X-E2E-Control`. Затем ждёт backend и проверяет сохранность настройки и отказ старому token. Без control-конфига эта проверка помечается `skip`.
5. Прямые API security checks: выбрать root приложения **без индексации**, запросить snippets `.env`/`password.txt` → 403 `FILE_FORBIDDEN`, sibling-prefix traversal → 403 `PATH_TRAVERSAL`. Тело неожиданно успешного secret snippet не читается.
6. Выбрать `scripts/e2e/fixture` через текстовое поле UI; ровно один запуск индексации одного TS файла, ожидание `ready` не более 180 секунд, без автоматического перезапуска при ошибках.
7. Ровно один UI search `calculateOrderTotal`, ссылки и TS snippet в Monaco; ровно один UI chat-вопрос об этой функции, видимые ответ и ссылки. Ответ должен объяснить скидку и получить `130` для `[100,50]` и скидки `20`; deterministic fallback «Нашел потенциально релевантные места в коде.» — ошибка, даже при HTTP 200. В chat-запросе запрещены Authorization и custom x-key заголовки.

Стоимость: одна маленькая индексация, один поиск и один chat (chat дополнительно выполняет внутренний retrieval backend). При сбое runner останавливается и **не повторяет платные циклы**. Он не вызывает clear-index, не удаляет БД, не меняет рабочие индексы. После успешного прогона повторный запуск снова имеет эту же стоимость.

## Бесплатный maintenance E2E

Запускайте после настройки backend-конфигурации в `apps/backend/.env` и готовности supervisor. Runner не читает содержимое защищённой конфигурации: её загружает само приложение.

```powershell
node --check scripts/e2e/run-maintenance.cjs
node scripts/e2e/run-maintenance.cjs
```

- Только фиксированные локальные frontend `127.0.0.1:5173` и backend `127.0.0.1:3181`; переменные альтернативных URL из раздела выше относятся лишь к `run.cjs`. Supervisor должен быть запущен обновлённым `serve.cjs`. Перед reset runner проверяет `.e2e-runtime/control.json` и авторизованный `GET /status` supervisor: `backendCwd`, `backendUrl`, `frontendUrl` должны подтверждать isolated cwd и локальные порты. Нет isolated БД или live-подтверждения — остановка **до reset**.
- Для входа используется `$env:E2E_ADMIN_LOGIN` (по умолчанию `admin`); пароль читается из корневого `password.txt` только в память. API-ключ не читается и не сохраняется. `hasApiKey` сравнивается до и после рестарта backend через supervisor, без изменения ключа.
- UI-вход: маскирование пароля, высота login/password `0.8 ± 0.02` от временного невидимого обычного input под label `14px` с глобальными стилями; остальные inputs сохраняют обычную высоту. Clone не получает `.admin-login-form` и удаляется сразу после замера.
- Проверяются 401 для неавторизованного статуса индексов, поля авторизованного ответа, текущая embedding model и counts в новой секции «Индексы». Для существующего legacy fixture требуется `requiresReset: true`; при отсутствии fixture/чанков именно эта проверка получает `skip`, искусственные данные не создаются.
- Inline-подтверждение reset: открытие → «Отмена» без reset HTTP; авторизованный `{confirm:false}` → 400 и неавторизованный reset → 401 без удаления. Затем ровно один авторизованный `{confirm:true}` через UI. Если индекс уже пуст и reset-кнопка недоступна, интерактивные reset-проверки помечаются `skip` — для полного прогона нужен оставшийся индекс от прежнего RAG E2E.
- После reset: `indexedProjects: 0`, `indexedChunks: 0`, `requiresReset: false`. Читается **исключительно** `.e2e-runtime/backend/data/app.sqlite` через `better-sqlite3` с `readonly: true`, `fileMustExist: true`; symlink/reparse-перенаправление cwd/БД отклоняется. Проверяются таблицы projects/files/chunks/conversations/messages, но имя таблицы embedding metadata не предполагается. Files/chunks должны быть пусты, project records (id/name/rootPath/createdAt) и полные строки conversations/messages — сохранены. Содержимое истории и контрольные суммы не выводятся. При пустой исходной истории проверка её сохранности остаётся, а отсутствие непустого fixture явно отражается как `skip`.
- После reload прежний fixture выбирается через UI/API, сохраняет id, получает `idle`, files/chunks `0`, chat input и отправка недоступны. Если project fixture отсутствует, соответствующий сценарий получает `skip`. Проверка очистки уже показанных references отмечена `skip`: runner не выполняет поиск ради наполнения UI.
- Стоимость **нулевая**: `/api/projects/index`, `/api/search`, `/api/chat/message` не вызываются. Browser observer считает обращения, routing блокирует запрещённые операции до отправки; сохранение API-ключа и старый per-project clear-index также запрещены. Нет mock/prod-fixture, автоматической переиндексации или платных повторов. Обычные select/status/restart не вызывают embedding/chat.
- Отчёт `reports/e2e/maintenance.json` содержит только стабильные имена проверок/коды, pass/fail/skip, HTTP-статусы нормализованных маршрутов, числовые ratios/counts. Нет паролей, ключей, token, HTML, названий/путей из БД, текстов чатов и сырых исключений. Скриншоты и запись трафика не включаются.

Для legacy-ветки используйте данные, уже оставшиеся после прежнего реального E2E **в isolated БД**. Maintenance reset глобален для всех проектов этой тестовой БД: старые индексы удаляются через административную UI-секцию, проекты и история чатов сохраняются. Рабочие данные приложения не затрагиваются. Не запускайте оба runner параллельно.

## Безопасный результат RAG runner

- Exit code `0` — все обязательные проверки прошли; `1` — ошибка.
- В терминале только статусы/стабильные коды и путь отчёта.
- `reports/e2e/latest.json` перезаписывается: pass/fail/skip, HTTP-статусы с нормализованными маршрутами (без query), безопасный статус/сообщение индексации и ответ о fixture. Нет HTML, request headers, credentials, конфигурации или token.
- Во время ввода проверяются маскирование, отсутствие секрета в видимом тексте, query-параметрах URL, localStorage/sessionStorage и API-ответах. После save/logout проверяется также отсутствие секрета в HTML. Для короткого пароля исключены совпадения со статическими стилями Monaco и точными заранее известными публичными именем/путём проекта; токены и длинный API-ключ проверяются также в полном HTML и URL. `value` собственного password input во время ввода не считается утечкой: React controlled input может синхронизировать этот атрибут.
- Login response token захватывается только в память для проверки отзыва; не сериализуется. Скриншоты, trace, HAR и сырые исключения не сохраняются ни при каких исходах.

Если тест остановился после сохранения ключа, ключ остаётся в `apps/backend/.env`, а тестовая БД — в `.e2e-runtime/backend/data`. Для диагностики используйте стабильный код и HTTP-статусы; не копируйте секретные ответы/конфигурацию в логи.
